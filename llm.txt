Tool: kazidoc
Package: @kazibee/kazidoc

Use this tool to work with Kazidoc projects as remote filesystems: navigate
folders, read and grep text files, write and edit documents, and reorganize the
tree. The client is multi-project: EVERY filesystem method requires an explicit
projectId (p_...) as its FIRST argument. Paths are project-relative
("notes/intro.md"). A pasted Kazidoc drive URL like
https://kazidoc.com/drive/p_abc123XYZ456/notes/intro.md is also accepted
anywhere a path is expected — the /drive/<project> prefix is stripped, and it
must match the projectId passed to the call (a mismatch fails fast).

Resolving the projectId
- getId(urlOrId) -> resolves a pasted drive URL (or bare p_... id) to a
  VERIFIED project id this key can access. Use this first when the user gives
  a URL.
- listProjects() -> [{ project_id, name }] for all accessible projects. Use
  when no URL is given and the target project is ambiguous.
- There is no bound/default project; never guess an id — resolve it.

Auth requirements
- KAZIDOC_API_KEY (kzd_...) — may access one or many projects.
- Optional KAZIDOC_API_URL for local dev (default https://api.kazidoc.com)
- If auth fails, instruct user to run: kazibee kazidoc login <API_KEY>

Typical intents to map (pid = resolved projectId)
- "which project is this URL"    -> getId(url)
- "what projects can I use"      -> listProjects()
- "what's in the project"        -> listdir(pid, path?)          ("" = root)
- "find where X is mentioned"    -> grep(pid, pattern, path?, include?)
- "read the doc"                 -> read(pid, path)
- "read part of a big file"      -> readRange(pid, path, startLine, endLine)
- "create/overwrite a doc"       -> write(pid, path, content)
- "change this text"             -> editReplace(pid, path, textToReplace, newContent)
- "add a line after X"           -> editInsert(pid, path, line, content)
- "remove this line"             -> editDelete(pid, path, line)
- "rewrite lines N-M"            -> readRange(...) then rangeReplace(pid, handleId, newContent)
- "re-indent this block"         -> readRange(...) then rangeIndent(pid, handleId, spaces)
- "show/view this image"         -> readImage(pid, path)
- "upload/save this image"       -> writeImage(pid, path, image, mediaType)
- "make a folder"                -> mkdir(pid, path)
- "rename/move"                  -> move(pid, from, to)
- "duplicate"                    -> copy(pid, from, to)
- "delete"                       -> delete(pid, path)

Reading rules (important)
- read() returns line-numbered content and is DENIED for files over 1000 lines
  (errorCode READ_TOO_LARGE). Do not retry the full read: grep() to locate the
  relevant line numbers, then readRange() for just that section.
- readRange() serves at most 1000 lines per call; endLine clamps to file length.
- Line numbers in returned content are display only — never include them when
  writing or editing.

Editing rules
- editReplace/editInsert/editDelete require EXACT, UNIQUE current text. On
  EDIT_AMBIGUOUS, expand the target with surrounding context; on EDIT_NO_MATCH,
  re-read the file first.
- rangeReplace/rangeIndent take the handleId from a readRange call. Handles are
  verify-at-use: if the file changed since the read, the call fails with
  STALE_HANDLE — call readRange again and retry with the fresh handle.
- Every error response includes errorCode, message, and requiredAction telling
  you exactly how to recover.

Image rules
- Images (png/jpeg/webp/gif/avif) are ordinary files at ordinary paths: they
  appear in listdir, and move/copy/delete work normally. Text operations on an
  image fail with NOT_TEXT_FILE (use readImage); readImage on a text file fails
  with NOT_IMAGE (use read). grep never matches images.
- readImage(pid, path) returns metadata plus a presigned URL valid for exactly
  300 seconds. Consume it immediately (fetch/view now). NEVER save the signed
  URL into a document, memory, or notes — it expires and is a bearer credential.
- To embed an image in Markdown, write a RELATIVE path, resolved against the
  document's folder: ![Diagram](./images/diagram.png)
- writeImage(pid, path, image, mediaType) accepts raw bytes (Uint8Array /
  ArrayBuffer / Blob), a base64 string, or a LOCAL FILE PATH string starting
  with "/", "./", "../", or "~/" (the sandbox needs read access to that
  directory — pass it via allowWorkspace). Max 10 MiB. The destination
  extension, mediaType, and actual bytes must agree (MIME_MISMATCH otherwise).
  SVG is not supported.
  Example: writeImage(pid, "docs/images/chart.png", "/tmp/chart.png", "image/png")

Linking between documents
- To link another document in Markdown, write a RELATIVE path resolved against
  the document's folder, exactly as the file is named — spaces and all. Kazidoc
  resolves relative link paths LITERALLY: never percent-encode them.
  [Workflow Nodes](<./Workflow Nodes.md>)   — correct (angle brackets when the
  path contains spaces)
  [Workflow Nodes](./Workflow%20Nodes.md)   — WRONG: resolves to a file
  literally named "Workflow%20Nodes.md" and renders Path not found.
- Absolute https://kazidoc.com/drive/... URLs are ordinary web URLs and DO use
  standard percent-encoding; the literal-path rule applies only to relative
  links.

CSV workbooks
- A FOLDER whose name ends in .csv (e.g. "pricing.csv") renders as one workbook;
  each *.csv file inside is a tab, ordered by filename (numeric prefixes like
  "01_" control order and are stripped from tab labels).
- "pricing.csv/index.css" styles every tab; "pricing.csv/02_by_region.csv.css"
  overrides one tab. Companion .css files are attached assets, not tabs.
- Build workbooks with ordinary mkdir + write calls — no special API.

Frames (interactive HTML/JS blocks in Markdown)
- The document IS the app: you can encode complete designs and behavior —
  dashboards, calculators, visualizations, interactive widgets — strictly
  inside a Markdown document. Nothing else to build, deploy, or host. When a
  user asks for anything interactive or designed, reach for a frame.
- A <frame> block inside a .md file renders in the Kazidoc document view as a
  LIVE sandboxed iframe: raw HTML + inline <script> + Tailwind utility classes
  (full Tailwind v4, arbitrary values included) — no build step, no CDN.
- Author it with ordinary write/edit calls. Delimiters must each sit alone on
  their own line at top level; the body is an HTML fragment (no <html>, <head>,
  <body>, <base>, or meta[http-equiv]):
  <frame height="480" title="Revenue dashboard">
  <div class="grid min-h-screen place-items-center bg-slate-950 text-white">
    <button id="counter" class="rounded-lg bg-blue-600 px-5 py-3">Count: 0</button>
  </div>
  <script>
    let n = 0;
    document.querySelector('#counter').addEventListener('click', (e) => {
      e.target.textContent = `Count: ${++n}`;
    });
  </script>
  </frame>
- Attributes (all optional, double-quoted only): height (int px, 160–2000,
  default 480), title (max 200 chars), and width — "content" (default, sits in
  the prose column), "wide" (breaks out of the column, centered, up to 75rem),
  or "full" (spans the whole document view). Unknown or malformed attributes
  make the frame render as a non-executable error card.
  Example: <frame width="full" height="600" title="Ops dashboard">
- The iframe's inner width follows its layout mode and the viewport; there is
  no fixed pixel width. Design responsively (Tailwind sm:/md:/lg: work), or
  constrain content yourself with e.g. <div class="max-w-md mx-auto">.
- Limits: max 8 frames per document, 256 KiB per frame body. Frames cannot
  nest. To SHOW frame syntax without running it, put it inside a fenced code
  block.
- Sandbox: frames get no Kazidoc API, cookies, network access, parent DOM, or
  message channel. External scripts, imports, fetch, and workers are blocked —
  keep everything inline and self-contained.
- Editing the document automatically replaces its frames with fresh ones; no
  extra call is needed.

Code call examples
Every sandbox module must use this entry-point shape:
```ts
export default async function ({ tools }) {
  const kazidoc = tools["kazidoc"];
  const pid = await kazidoc.getId("https://kazidoc.com/drive/p_abc123XYZ456");
  const root = await kazidoc.listdir(pid);
  return root;
}
```

Within that function, calls look like:
```ts
const pid = await tools["kazidoc"].getId(userSuppliedUrl);
const doc = await tools["kazidoc"].read(pid, "notes/intro.md");
const hits = await tools["kazidoc"].grep(pid, "pricing", undefined, "*.md");
await tools["kazidoc"].write(pid, "notes/summary.md", "# Summary\n\n...");
const range = await tools["kazidoc"].readRange(pid, "notes/long.md", 120, 160);
if (range.ok) await tools["kazidoc"].rangeReplace(pid, range.handleId, "new section text");
await tools["kazidoc"].mkdir(pid, "pricing.csv");
await tools["kazidoc"].write(pid, "pricing.csv/01_summary.csv", "region,price\neast,10");
await tools["kazidoc"].move(pid, "notes/draft.md", "archive/draft.md");
```

Always check `.ok` before using a result; on `ok: false`, follow `requiredAction`.
